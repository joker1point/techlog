## 从参考项目移植功能的标准流程

在独立开发过程中，我们经常会遇到这样的场景：发现某个开源项目有个很棒的功能，想移植到自己的项目里。但真正动手时，往往会陷入"看懂了代码，却不知道从哪里开始"的困境。

经过多次实践，我总结出一套**从参考项目移植功能的标准流程**，适用于 Python/FastAPI + Streamlit 技术栈，也可以推广到其他技术栈。

---

### 为什么需要标准流程？

移植功能不是简单的"复制粘贴"。它涉及：

1. **技术栈差异** — 参考项目可能用 React，而你的项目用 Streamlit
2. **架构适配** — 参考项目的架构未必适合你的项目
3. **数据模型迁移** — 涉及数据库的部分需要 careful 处理
4. **安全考量** — 避免引入敏感信息或安全漏洞

没有标准流程，很容易做多了、做偏了，或者踩一堆不必要的坑。

---

## 标准流程：7 步法

```
1. 分析参考项目
        ↓
2. 确认集成范围（关键！）
        ↓
3. 数据模型 + 迁移设计
        ↓
4. 后端实现（分层）
        ↓
5. 前端实现
        ↓
6. 端到端验证
        ↓
7. 提 PR
```

---

## 步骤 1：分析参考项目

**目标**：理解参考项目的功能和技术栈。

**具体做法**：

1. 用 `WebFetch` 抓取参考项目的 README / 关键源码文件
2. 识别可移植的核心能力（如：会话管理、API 测试面板、设置页）
3. 记录参考项目的技术栈（React/Vite/Next.js 等）与当前项目的差异

**输出**：一份简单的功能清单，列出"要移植什么"。

---

## 步骤 2：确认集成范围（关键！）

> **不要跳过这一步直接写代码，否则容易做多了或做偏了。**

用提问的方式与自己（或团队成员）对齐：

| 问题 | 选项 |
|------|------|
| **集成方式** | 后端端口 + 前端页面 / 完整移植原版 UI / 仅后端能力 |
| **核心特性** | 多选需要的能力（如 models 列表、流式延迟、探针） |
| **配置继承** | 是否从现有设置页继承 provider/API key |

**为什么这步关键？** 因为参考项目的功能可能很丰富，但你不一定都需要。明确范围可以避免做无用功。

---

## 步骤 3：数据模型 + 迁移设计

如果功能涉及持久化（如会话管理），这步尤其重要。

### 3.1 新增模型

在 `models.py` 加表 + 外键（**优先 `ON DELETE CASCADE`**）：

```python
class Conversation(Base):
    __tablename__ = "conversations"
    id = Column(Integer, primary_key=True)
    session_id = Column(String, nullable=False)
    character_id = Column(Integer, ForeignKey("characters.id", ondelete="CASCADE"))
    updated_at = Column(DateTime, default=datetime.utcnow)
```

### 3.2 迁移脚本

写**幂等迁移**（`db_migration.py`），处理存量数据回填：

```python
# 幂等：检查列是否存在再 ALTER TABLE
cols = _sqlite_columns(engine, "conversations")
if "session_id" not in cols:
    conn.execute(text("ALTER TABLE conversations ADD COLUMN session_id ..."))

# 回填：为孤儿数据创建"默认记录"并 UPDATE 关联
```

**关键点**：
- 幂等：迁移脚本可重复运行不报错
- 回填：为孤儿数据创建"默认记录"并 UPDATE 关联

### 3.3 复合索引

为高频查询模式建索引（如 `character_id + updated_at desc`）。

---

## 步骤 4：后端实现（分层）

按以下顺序写，**每层写完跑一次 `ast.parse` 语法检查**：

### 4.1 Service 层（`backend/services/xxx.py`）

核心业务逻辑，**纯函数式**，不依赖框架：

```python
def get_conversations(db, character_id=None):
    query = db.query(Conversation)
    if character_id:
        query = query.filter(Conversation.character_id == character_id)
    return query.order_by(Conversation.updated_at.desc()).all()
```

### 4.2 Schema 层（`schemas.py`）

Pydantic 请求/响应模型：

```python
class ConversationCreate(BaseModel):
    session_id: str
    character_id: int

    model_config = SettingsConfigDict(extra="ignore")  # 避免 .env 多余字段报错
```

> **踩坑**：Pydantic `BaseSettings` 加 `extra="ignore"` 避免 .env 多余字段报错。

### 4.3 Endpoint 层（`main.py`）

薄路由，调 service + 异常映射：

```python
@app.post("/api/conversations", response_model=ConversationResponse)
def create_conversation(req: ConversationCreate, db: Session = Depends(get_db)):
    try:
        return service.create_conversation(db, req)
    except Exception as e:
        raise HTTPException(status_code=400, detail=str(e))
```

### 4.4 启动钩子

在 `startup_event` 中调 `run_all_migrations(engine)`。

---

## 步骤 5：前端实现

### 5.1 API 客户端（`api_client.py`）

每个后端端点对应一个函数，统一 `_handle_response` + 超时：

```python
def create_conversation(session_id, character_id):
    return _handle_response(requests.post(
        f"{API_BASE}/conversations",
        json={"session_id": session_id, "character_id": character_id},
        timeout=5
    ))
```

### 5.2 页面实现（`app.py`）

新增 `render_page_xxx()`，注册到侧边栏导航。

### 5.3 UI 交互

- 列表用 `st.dataframe`，操作用 `st.popover`（二次确认删除）
- 跨组件状态用 `st.session_state`，切换实体时重置缓存
- 双栏布局用 `st.columns([1, 2.5])`

---

## 步骤 6：端到端验证

**目标**：确保功能真正可用。

**验证清单**：

1. 重启后端，观察迁移日志（确认回填数量）
2. 用 PowerShell `Invoke-WebRequest` 逐个调 API 端点
3. 写临时验证脚本调 `api_client` 函数（用完删除）
4. 重启前端，确认页面无报错

**验证脚本模板**：

```
创建 → 操作 → 搜索 → 删除 → 确认消失
```

---

## 步骤 7：提 PR

### 7.1 提交前安全检查

- **重建 `.gitignore`**：排除 `.env`、`data/`、`usercontext/`、`refproj/`、`__pycache__/`、`*.log`
- **只 stage 主题相关文件**：明确列出文件名，不用 `git add .`
- **不纳入无关删除**：工作区可能有旧文件删除，不混入本次 PR

### 7.2 分支与提交

```powershell
# 用 git switch（Git 2.23+，比 checkout 更安全）
git switch -c feature/xxx

# 明确列出文件
git add backend/services/xxx.py backend/main.py frontend/app.py

# PowerShell 不支持 bash heredoc，用 -F 文件方式提交
git commit -F commit_msg.txt
```

> **踩坑**：PowerShell 终端不兼容 `$(cat <<'EOF' ... EOF)`，commit 会卡住。解决：把消息写到临时文件，用 `git commit -F`。

### 7.3 推送与创建 PR

```powershell
# push 到 fork remote
git push -u fork feature/xxx

# 用 gh CLI 创建跨 fork PR（GitHub MCP token 可能失效）
$env:GH_TOKEN="<token>"
gh pr create --repo <上游owner>/<repo> --head <forkowner>:feature/xxx --base main --title "..." --body-file pr_body.md
```

---

## 常见踩坑速查

| 现象 | 原因 | 解决 |
|------|------|------|
| Pydantic ValidationError extra inputs | .env 有未声明字段 | `model_config = SettingsConfigDict(extra="ignore")` |
| URL 拼出 `/v1/v1/models` | base_url 已带 `/v1` | 写 `_join_url()` 去重 |
| commit 卡在 `>>` 提示符 | PowerShell 不支持 heredoc | `git commit -F file.txt` |
| GitHub MCP Bad credentials | MCP token 过期 | `gh` CLI + `GH_TOKEN` |
| cross-repo PR "No commits" | push 到了非 fork 仓库 | 确认 fork 关系，push 到正确 remote |
| 迁移重复执行报错 | ALTER TABLE 非幂等 | 先 `PRAGMA table_info` 检查列是否存在 |
| git log 进 pager 卡住 | PAGER 未设置 | `git --no-pager log` |
| 敏感文件被 stage | .gitignore 缺失 | 提交前重建 .gitignore，只 add 明确文件 |

## 移植决策原则

1. **逻辑集中后端** — 测试/业务逻辑放后端 service，前端只做展示。便于复用与测试。

2. **配置继承** — 新功能优先复用现有设置（如 LLM provider 配置），避免重复输入。

3. **合理简化** — 用当前栈的等价组件替代原版（如 Streamlit `st.popover` 替代 React inline edit）。

4. **安全脱敏** — 探针/调试接口的请求头密钥字段替换为 `***`。

5. **幂等迁移** — 迁移脚本可重复运行不报错，存量数据自动回填。

---

## 结语

移植功能不是目的，**理解并复用优秀的实现**才是。这套流程的核心思想是：

- **先想清楚，再动手** — 步骤 1-2 是关键
- **分层实现，逐层验证** — 避免一次性写一大堆代码
- **记录踩坑** — 下次遇到同样问题，直接查表解决

希望这套流程能帮你更高效地移植功能，少踩坑，多产出。
